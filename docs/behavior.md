# How the app reads and saves a session

Part of the L2Tracker Companion's developer notes (see the README). The decisions below each exist because of a real failure; read the relevant paragraph before changing the polling, the save gate or the spot logic.

**Session store:** each successful parse (WPF or `ocr-parse.sh`) appends a snapshot to `%LOCALAPPDATA%\L2TrackerCompanion\session.db` unless monotonicity rejects it. The WPF window lists those rows. A session begins when the player resets the Play Report **in-game**, which the app detects on its own (see *Reset detection* below). The only "new session" control is the **Start a new session** link beside Save, shown while tracking is stopped and a save is possible: it starts a fresh run, as **Start tracking** does. The buffer is also cleared when the app starts and whenever **Start tracking** is pressed (together with the last verified reading Save and Live were holding), so a stale baseline is never more than one button away from being discarded.

**Offline parsing does not touch the live session.** *Capture once* reads the panel as it is now and counts as a real reading; *Parse last capture* and *Parse a PNG…* re-read a file that may be hours old, which is indistinguishable from a fresh reset – they print into the debug parse pane and store nothing (Live, the picker, and Save stay on the tracking session). After a successful Save, Capture once does not refill Live until **Start tracking**.

**Polling:** **Start tracking** captures → OCR → accept-or-discard every 10s until **Stop tracking**. A run opens at 2s instead, until the location run has its four readings or the attempt ceiling is reached – see *Warm-up* below. The buttons control whether the app is looking at the screen; they do not open or close a session. A tick whose XP / Adena / play time dropped versus the last accepted snapshot is discarded (OCR misread) and does not replace the live totals or the Save payload. Lamp XP is monotonic only when both ticks had `lampXpRead`; a closed Magic Lamp panel is not a misread. A tick that finishes after Stop does not append.

**Warm-up:** a run polls at `PollingLoop.WarmUpInterval` (2s) instead of 10s until it has gathered `WarmUpReads` readings (4, the same number as `LocationStability.RunLength`), because at the steady cadence a new spot cannot settle for the first forty seconds of a session. The gap is measured **from the end of each tick, not its start**: a capture plus OCR can outlast 2s, and the reentrancy guard in `RunPollTickAsync` drops a tick that lands on a busy one – so the timer is re-armed after each warm-up tick finishes, and the real cadence is "2s, or the tick's own duration, whichever is longer".

Only a reading that actually **reached** the run counts towards those four: it has to be appended *and* carry a non-empty `locationHint`, matching what `LocationStability` itself counts. An attempt that captured nothing (Start pressed before the game was launched), failed to parse, was discarded by monotonicity, or read no minimap name contributes nothing and so spends nothing. Whenever the buffer is dropped – in-game reset, `StaleBaselineStrikes`, a restarted client – the gathered hints go with it, so the reads counted towards the run are given back too. What bounds the fast cadence instead is `MaxWarmUpAttempts` (3× the run): with the game closed no attempt ever becomes a reading, and without a ceiling the 2s polling would never stop.

Giving those reads back can put a run **back** into warm-up mid-session, and that is deliberate – a wipe empties the location run, which is the exact state the warm-up exists for. It cannot run away: the attempt ceiling is spent across the whole run and is never given back, so after roughly the first two minutes (4 warm-up plus 10 steady ticks) no wipe can warm up again. A location *change*, which wipes nothing, always refills at the steady cadence. The cost of a warm-up tick is small enough that this is not worth gating: the synchronous capture blocks the WPF UI thread for ~100ms (measured; the first capture of a process is ~1.1s while Direct3D initialises) and OCR runs off it, so 2s polling holds the UI for under 4% of the time rather than freezing it. Nothing about accuracy changes: Save posts a single frame, so more frequent readings are more samples of the same OCR, not better OCR.

**Reset detection:** because the player restarts the Play Report in-game to begin a session, the panel legitimately drops – so a drop is no longer automatically a misread. Four layers, because no single one covers every route:

1. **The client went away and came back under a new process id** (`GameProcessWatch`) – a restarted client always comes back with a zeroed panel. A changed id on its own is not enough: the app follows whichever client is in front, so with two clients open the id flips on every alt-tab, and again when one of the two is closed. The app has to have observed *no* game window at all in between.
2. **A coherent drop**: the duration went backwards *and* XP actually fell *and* Adena did not grow, with every field readable. There is deliberately **no ceiling** on how far the new duration may have advanced: whether the reset is caught in its first minute or its fifteenth depends only on when a tick happened to land, and readings stop landing for ordinary reasons (panel closed, client relogged, tracking paused). XP has to have *fallen*, not merely failed to grow – an unchanged XP beside a shorter duration is the duration line being misread.
3. **`StaleBaselineStrikes` (3) rejections in a row** against the same stored row: a real misread is transient, so several in a row mean the stored row is the stale thing. It is dropped and counting restarts.
4. **Pressing Start tracking**, and starting the app, clear the buffer outright.

Anything else stays a misread and is discarded. Mistaking a misread for a reset costs a dropped buffer and nothing more – the save is built from a single frame.

**Live status:** a traffic light on the latest parse (not only accepted snapshots). Red = unread farm field, a lamp table that is in frame but unreadable, a discarded tick, or a failed capture; orange = Magic Lamp panel closed; green = farm + lamps read. Missing minimap hint does not change the colour. Updates every poll tick. XP, Adena, lamps, and live rates on the card are the **last verified frame** (the same numbers Save would post), not the rejected OCR – a red/orange light still explains this tick, but it does not wipe the totals.

**Save session:** Save POSTs **one Play Report reading** as a `FarmLog` (`xpFarmed` / `adena` / lamp XP **in thousands**, `minutes` taken from the Play Report's own duration, `% Bonus` = `acquiredXpSp`) – the current tick when it is trustworthy, otherwise the last verified stored frame. The panel is already a complete session record, so nothing is subtracted and the wall clock is not consulted – a log can be saved long after the farming stopped, and the companion need not have been running for it.

Save is gated by `SaveGate`, which trusts a frame on **in-frame agreement** rather than repetition – OCR of an unchanged screen is deterministic, so re-reading a static panel would only reproduce the same misread. The current tick is blocked when: the play-time dual-read contradicted itself, the two Adena reads disagreed, the two XP reads disagreed on digit count, XP / Adena / play time are unread, play time is 0, the Magic Lamp panel is closed or its XP column unread (no silent zeros), lamp XP exceeds dialog XP, or the previous tick was a misread. A rejected tick does **not** disable Save: the button posts the **last verified frame** (the newest stored snapshot that itself passes the gate). A closed lamp panel is still stored for monotonicity and location, but it is skipped as a save payload so the previous open-panel reading remains available. A spliced XP figure warns (orange) but still saves – and the warning **names both competing figures** ("XP disputed – token read 4,210,400, crop read 9,210,400. Saving 9,210,400 (spliced)") so the player, who has the panel on screen, can settle it at a glance. A blocked Adena says the same, which distinguishes a dropped digit from a failed read. Duplicate POSTs of the same (or a later) Play Report are allowed: one in-game session may become several farm logs, including the same stretch more than once.

After a successful Save the WPF app **stops** the 10s tracking loop and clears the companion session: snapshot buffer, last reading, Live status, and the spot picker. Character and bonus stay. Poll ticks, Capture once, and Parse last capture do not refill Live until **Start tracking**. Duplicate POSTs of the same Play Report are still allowed – Start tracking to capture it again, then Save. The session-status line keeps the confirmation until **Start tracking**, sign-out, or a game restart.

```bash
./scripts/save.sh --character-id <id> [--spot-id <id>] [--bonus <n>]
```

It saves the most recent **verified** stored reading (skipping later ticks that would not pass the gate), subject to the same checks. Omit `--spot-id` to resolve the spot the same way the window does.

**Spot follow:** one flag, `UserChose`. It starts clear. A manual pick sets it. Clear, a character change, sign-out, a reloaded spot list, or a successful save clears it, so the current reading can set the spot again. While it is clear, a minimap `locationHint` that exactly names one owned spot (case-insensitive, never the area label) sets the picker immediately, and a later exact hit on a different place may replace that automatic choice (`Spot switched to "…"`). A read that matches nothing leaves the automatic spot in place. A hint that is the same place as the current spot – including an artifact that rewrites two or three letters of a longer word – does not move the picker. Short tokens such as east/west still have to match exactly. A discarded OCR tick does not move the picker. Never auto-saves.

A name that is **not** already a spot is created only at Save, and only when the picker is empty, the last 4 non-empty hints are the same place as each other, and the frame being saved is still that place. The spelling kept is the one that occurs most often in that run. A garbled name that is the same place as exactly one owned spot selects that spot instead of creating another; several such spots ask for a pick. A spot whose name is the official reading plus the player's own trailing words (`Hot Springs Top` for `Hot Springs`) counts as that place: one such spot is selected with no line under the picker. Several preselect the alphabetically first (`Hot Springs Low` before `Hot Springs Top`) and keep `Multiple spots match "…" – pick one` until the player picks; Save stays enabled on that preselection. An exact list name still wins over those suffixes, and an automatic spot for a different place is not replaced. If the frame being saved is a different place, Save does not create or attach from the run. An exact hit on that frame still selects the owned spot. Once the player has chosen, detection stops for that run and does not overwrite the picker. The line under the picker stays empty once a single spot is settled, apart from the one-tick `Spot switched to "…"` notice. Clear is shown only after a manual pick. It drops that choice and lets the current reading set the spot again, then hides. A settled move to a different place still reminds them to restart the in-game Play Report, because the panel totals cover the whole session.

```bash
./scripts/ocr-parse.sh --match-hint /path/to/hud.png
```

Uses the stored JWT. Switching character in the window reloads spots.

**Live rates:** the live-status card (and `ocr-parse.sh` / `--parse`) shows XP and Adena rates from the **current screenshot**: raw OCR XP and Adena divided by OCR play-time minutes, rounded away from zero. The WPF Session tab uses the signed-in account's `rateUnit` setting from `GET /api/settings` (`minute` → XP/min, `hour` → XP/h; Prisma default is `hour`). Settings are re-fetched when tracking starts. CLI parse output stays per minute. Display-only: Save posts one Play Report reading, with the minutes taken from the panel's own duration, and these figures are not converted to thousands. Play time must be greater than 0; otherwise both rates show `(need play time)`. Unread XP still allows Adena rate and the reverse. Dialog XP includes lamps, so a Magic Lamp pop jumps the XP rate. Play Report time is whole minutes (the rate only moves when that digit or the totals change) and is the panel's own duration, not this companion session.

**Spot benchmark:** under the live rates the card ranks the current reading against the spots this character has already farmed – `XP/h: #2 of 9 spots`, plus the same line for Adena. Averages come from the `farmXpHourly` / `adenaHourly` / `averageXpHourly` fields of `GET /api/spots?characterId=`, which the app already calls for the Spot picker, so no extra request and no backend change; the XP rank uses `averageXpHourly` (raw, lamps included) because the live reading includes lamps too. Those figures are **per character** – a spot only enters the pool, and the denominator, once this character has logged there. `logCount` is deliberately unused: it counts every character on the account. API amounts are in thousands and live readings are raw, so the averages go through `LegacyThousands.ToRaw` – delete that class together with the `Amounts.ToThousands` convention when the project drops the ×1000 storage. A **Compare against** picker narrows the pool to one Area (all of the account's areas are listed, including ones with no history); the choice is not persisted between runs. Deliberately a rank and nothing else: the Play Report counts from login, so a reading taken after moving spots blends both, which would make any "vs this spot's average" figure wrong. For the same reason a settled move to another location shows a one-line reminder to restart the in-game Play Report – a reminder only, nothing is blocked. The card is silent while spots are still loading, and hides with the rest of the data on a red light.
